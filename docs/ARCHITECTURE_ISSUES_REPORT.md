# 🏗️ Архитектурные проблемы проекта TTS_TTV_0.02

**Дата:** 10 ноября 2025  
**Статус:** 🔍 Обнаружено

---

## 📋 Критические архитектурные проблемы

### 1. ❌ КРИТИЧНО: Избыточное количество контекстов (9 контекстов)

**Проблема:**
- Слишком много контекстов создает сложную иерархию зависимостей
- Каждый контекст управляет своим собственным состоянием и загрузкой данных
- Нет единого источника истины для состояния приложения

**Контексты:**
1. `AuthContext` - аутентификация
2. `ChatContext` - сообщения чата
3. `DataContext` - данные стрима (title, category)
4. `PlayerContext` - YouTube плеер
5. `TtsContext` - TTS настройки
6. `TtsHealthContext` - TTS health check
7. `IntegrationsContext` - интеграции (Twitch, VK, DonationAlerts)
8. `UserSettingsContext` - пользовательские настройки
9. `DonationAlertsContext` - DonationAlerts интеграция

**Риски:**
- Сложность понимания потока данных
- Проблемы с синхронизацией состояния
- Избыточные ре-рендеры
- Сложность тестирования
- Проблемы с производительностью

**Решение:**
- Объединить связанные контексты (например, `TtsContext` + `TtsHealthContext`)
- Использовать React Query для управления серверным состоянием
- Оставить только UI состояние в контекстах
- Создать единый `AppStateContext` для глобального состояния

---

### 2. ❌ КРИТИЧНО: Отсутствие единого слоя для API вызовов

**Проблема:**
- `botService.get/post/put/delete` вызывается напрямую из компонентов (176 мест)
- Нет абстракции над API
- Дублирование логики запросов
- Нет единого места для обработки ошибок
- Сложно тестировать и мокировать

**Текущая структура:**
```javascript
// Компонент напрямую вызывает API
const response = await botService.get('/api/tts/status');
```

**Риски:**
- Сложность рефакторинга API
- Невозможность централизованной обработки ошибок
- Дублирование кода
- Сложность добавления логирования/мониторинга
- Нарушение принципа Single Responsibility

**Решение:**
- Создать слой сервисов (Service Layer)
- Инкапсулировать все API вызовы в сервисы
- Использовать React Query для кэширования и синхронизации
- Централизованная обработка ошибок

---

### 3. ❌ КРИТИЧНО: Смешанные паттерны управления состоянием

**Проблема:**
- Context API для глобального состояния
- React Query для серверного состояния (частично)
- Ручной кэш (localStorage, CacheManager)
- Локальное состояние (useState)
- Нет единого подхода

**Примеры:**
```javascript
// Context API
const { user } = useAuth();

// React Query
const { data } = useQuery(['commands'], fetchCommands);

// Ручной кэш
const cached = getQueryCache(['stream-data', user?.id]);

// Локальное состояние
const [loading, setLoading] = useState(false);
```

**Риски:**
- Путаница в выборе подхода
- Дублирование логики
- Проблемы с синхронизацией
- Сложность поддержки

**Решение:**
- **React Query** для всего серверного состояния
- **Context API** только для UI состояния (theme, modals, etc.)
- **Zustand/Jotai** для сложного клиентского состояния (опционально)
- Удалить ручной кэш, использовать React Query

---

### 4. ❌ КРИТИЧНО: Сложные зависимости между контекстами

**Проблема:**
- `AuthContext` используется во всех контекстах
- `IntegrationsContext` зависит от `AuthContext`
- `ChatContext` зависит от `AuthContext` и `IntegrationsContext`
- `DataContext` зависит от `AuthContext` и `IntegrationsContext`
- `PlayerContext` зависит от `AuthContext` и `ChatContext`

**Цепочка зависимостей:**
```
AuthContext
  ↓
IntegrationsContext
  ↓
ChatContext, DataContext, PlayerContext
  ↓
TtsContext, UserSettingsContext
```

**Риски:**
- Сложность понимания порядка инициализации
- Проблемы с циклическими зависимостями
- Избыточные ре-рендеры при изменении верхнего контекста
- Сложность тестирования

**Решение:**
- Упростить зависимости
- Использовать React Query для независимой загрузки данных
- Использовать события для синхронизации (CustomEvents)
- Разделить контексты на независимые модули

---

### 5. ❌ КРИТИЧНО: Дублирование логики загрузки данных

**Проблема:**
- Каждый контекст загружает данные по-своему
- Дублирование логики кэширования
- Дублирование обработки ошибок
- Дублирование loading состояний

**Примеры:**
```javascript
// AuthContext
const checkAuthStatus = useCallback(async (force = false) => { ... });

// DataContext
const loadStreamData = useCallback(async (force = false) => { ... });

// ChatContext
const loadChatHistory = async () => { ... };

// PlayerContext
const loadQueue = useCallback(async (force = false) => { ... });
```

**Риски:**
- Дублирование кода
- Неконсистентное поведение
- Сложность поддержки
- Проблемы с синхронизацией

**Решение:**
- Использовать React Query для всех загрузок данных
- Единый паттерн для всех API вызовов
- Централизованная обработка ошибок
- Единый подход к loading состояниям

---

### 6. ⚠️ ВАЖНО: Отсутствие единого обработчика ошибок

**Проблема:**
- Обработка ошибок разбросана по всем компонентам
- Нет единого места для логирования ошибок
- Разные подходы к обработке ошибок
- Нет централизованного error reporting

**Текущая ситуация:**
- `botService.interceptors.response` - частичная обработка
- `api.interceptors.response` - частичная обработка
- Компоненты обрабатывают ошибки по-своему
- `ErrorBoundary` только для React ошибок

**Риски:**
- Неконсистентная обработка ошибок
- Сложность отслеживания ошибок
- Плохой UX при ошибках
- Нет мониторинга ошибок

**Решение:**
- Единый error handler
- Централизованное логирование
- Error reporting service (Sentry, LogRocket)
- Единый UI для отображения ошибок

---

### 7. ⚠️ ВАЖНО: Смешение ответственности в контекстах

**Проблема:**
- Контексты делают и состояние, и загрузку данных, и бизнес-логику
- Нарушение принципа Single Responsibility
- Сложность тестирования
- Сложность рефакторинга

**Пример:**
```javascript
// ChatContext делает все:
// 1. Управление состоянием сообщений
// 2. Загрузка истории из API
// 3. WebSocket подключение
// 4. Обработка сообщений
// 5. Логика фильтрации
```

**Риски:**
- Нарушение SOLID принципов
- Сложность тестирования
- Сложность рефакторинга
- Проблемы с производительностью

**Решение:**
- Разделить ответственность:
  - **Контексты** - только UI состояние
  - **React Query** - серверное состояние
  - **Сервисы** - бизнес-логика
  - **Хуки** - переиспользуемая логика

### 8. ⚠️ ВАЖНО: Дублирование API клиентов

**Проблема:**
- `botService` (axios instance)
- `api` (axios instance)
- `adminApi` (axios instance)
- `ttsService` (axios instance)
- Разные interceptors, разные настройки

**Риски:**
- Дублирование кода
- Неконсистентное поведение
- Сложность поддержки
- Проблемы с CORS и credentials

**Решение:**
- Единый API клиент с конфигурацией
- Разные instances только при необходимости (разные baseURL)
- Единые interceptors
- Единая обработка ошибок

### 10. ⚠️ ВАЖНО: Проблемы с производительностью

**Проблема:**
- Много контекстов = много ре-рендеров
- Нет мемоизации в некоторых местах
- Дублирование запросов (частично исправлено)
- Нет виртуализации для больших списков

**Риски:**
- Медленная работа при большом количестве данных
- Избыточные ре-рендеры
- Проблемы с производительностью

**Решение:**
- Оптимизация контекстов (разделение на мелкие)
- Мемоизация вычислений
- Виртуализация списков (react-window, react-virtual)
- Code splitting и lazy loading

                         ↓

                         ↓
┌─────────────────────────────────────────────────────────┐

│  - API Services (инкапсуляция API вызовов)              │

│  - Error Handling (централизованная обработка)          │
└─────────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────────┐
│                    API Client Layer                      │
│  - Единый API клиент (axios instance)                   │
│  - Interceptors (auth, errors, logging)                 │
│  - WebSocket client (SharedWebSocketManager)            │
└─────────────────────────────────────────────────────────┘

## 🔍 Дополнительные проблемы

### 11. ⚠️ СРЕДНЕ: Дублирование React Query queries

**Проблема:**
- Один и тот же query может вызываться в разных компонентах
- Нет единого места для определения queries
- Дублирование query keys

**Риски:**
- Неконсистентные query keys
- Сложность синхронизации
- Проблемы с инвалидацией

**Решение:**
- Создать `queryKeys.js` с централизованными ключами
- Создать `queries.js` с переиспользуемыми query функциями
- Использовать query factories

---

### 12. ⚠️ СРЕДНЕ: Нет единого подхода к синхронизации состояния

**Проблема:**
- CustomEvents для синхронизации (drops-config-changed, tts-settings-changed)
- React Query для серверного состояния
- WebSocket для real-time обновлений
- Context API для UI состояния
- Нет единого паттерна

**Риски:**
- Путаница в выборе подхода
- Проблемы с синхронизацией
- Сложность отладки

**Решение:**
- Единый паттерн для синхронизации
- React Query для всего серверного состояния
- WebSocket только для real-time событий
- Убрать CustomEvents, использовать React Query invalidation

---

### 13. ⚠️ СРЕДНЕ: Сложная иерархия провайдеров

**Проблема:**
- Много уровней вложенности провайдеров
- Сложность понимания порядка инициализации
- Проблемы с производительностью

**Текущая структура:**
```
QueryClientProvider
  → BrowserRouter
    → ConditionalContextWrapper
      → CoreProviders (composeProviders)
        → ToastProvider
        → AuthProvider
        → IntegrationsProvider
        → ChatProvider
        → UserSettingsProvider
          → App
            → Layout
              → TtsHealthProvider (локальный)
              → PlayerProvider (локальный)
              → DonationAlertsProvider (локальный)
```

**Риски:**
- Много ре-рендеров при изменении верхнего контекста
- Сложность тестирования
- Проблемы с производительностью

**Решение:**
- Упростить иерархию
- Использовать React Query для серверного состояния
- Локальные провайдеры только для UI состояния
- Разделить на независимые модули
